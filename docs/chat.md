# Архитектура контекста чата

Для первой версии выбрана стратегия `sliding window`.

Почему именно она:
- для первой сборки нужен предсказуемый и простой контракт без второго LLM-вызова на суммаризацию;
- её проще отлаживать и тестировать на JSON и Postgres-репозиториях;
- для FAQ-бота и базового сценария техподдержки последних сообщений обычно достаточно;
- она не вносит дополнительную задержку перед ответом модели.

Как это работает:
- сервис запрашивает у репозитория последние `N` сообщений, где `N` берётся из `CHAT_CONTEXT_WINDOW`;
- если у чата задан `system_prompt`, он добавляется в начало контекста;
- затем применяется токен-бюджет: `CHAT_CONTEXT_WINDOW_TOKENS - CHAT_RESPONSE_TOKENS - CHAT_SAFETY_MARGIN`;
- если бюджет превышен, история режется с начала, но системное сообщение сохраняется.

Гибридная стратегия `hybrid` тоже поддержана кодом как расширение, но для основной документации и обоснования выбрана `sliding`, потому что она лучше соответствует цели первой поставки: быстро получить стабильный backend-контракт `/chats/{id}/messages`.
