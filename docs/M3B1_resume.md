# Текущий этап проекта: Function Calling для ассистента техподдержки

## 1. Общая цель

В проекте реализован учебный, но рабочий полный цикл **Function Calling** для ассистента технической поддержки.

Предметная область: ассистент техподдержки, который отвечает на вопросы пользователей, разбирает технические проблемы, ошибки приложений, сбои АИС и при необходимости ищет типовое решение в базе знаний.

Основной реализованный tool:

```python
search_knowledge_base(query, ips)
```

Назначение: поиск типовых решений в базе знаний техподдержки.

Параметры:

```text
query — краткое описание проблемы пользователя;
ips — одно ответственное подразделение или группа поддержки.
```

Допустимые значения `ips`:

```text
""
"АИС Правоохрана"
"АИС ЦРСВЭД"
"АИС Постконтроль"
```

Если подразделение не указано или его нельзя определить из запроса пользователя, в `ips` передаётся пустая строка.

## 3. Реализована JSON Schema для tool

Tool описан в файле:

```text
app/tools/schemas.py
```

Схема построена для OpenAI Chat Completions API в формате:

```python
{
    "type": "function",
    "function": {
        "name": "search_knowledge_base",
        "description": "...",
        "parameters": {...}
    }
}
```

Основные моменты схемы:

```text
1. query — string, обязательный параметр, minLength = 3.
2. ips — string, обязательный параметр.
3. ips ограничен через enum.
4. additionalProperties = False.
5. description для tool подтягивается из отдельного markdown-файла.
```

Важно: параметр `ips` в этом проекте — это не IP-адрес, а ответственное подразделение или АИС.

## 4. Tool description вынесен в отдельный файл

Описание tool хранится отдельно:

```text
app/prompts/tools/search_knowledge_base.md
```

В description указано, когда модель должна вызывать tool:

```text
- если пользователь описывает конкретную техническую проблему;
- если есть ошибка, симптом сбоя, название сервиса или АИС;
- если пользователь просит найти типовое решение.
```

И когда tool вызывать не надо:

```text
- для общих теоретических вопросов;
- для объяснения терминов;
- для обычной беседы;
- для задач без привязки к конкретной ошибке или технической проблеме.
```

## 5. Реализован system prompt

System prompt вынесен в файл:

```text
app/prompts/system_v1.j2
```

В нём описана роль ассистента:

```text
Ты ассистент технической поддержки.
```

Основные правила:

```text
1. Если пользователь описывает конкретную проблему или ошибку — использовать tool поиска по базе знаний.
2. Не выдумывать решения из базы знаний.
3. Для общих вопросов отвечать без tool.
4. Если указана АИС или подразделение — передать его в ips.
5. Если подразделение не указано — передать пустую строку.
6. В финальном ответе не показывать пользователю tool_call_id, JSON-аргументы и служебные поля SDK.
```

## 6. Реализован loader промптов

Файл:

```text
app/prompts/loader.py
```

В нём реализованы функции:

```python
load_prompt(file_name: str, **context: object) -> str
load_text_prompt(relative_path: str) -> str
```

`load_prompt()` используется для Jinja2-шаблонов, например `system_v1.j2`.

`load_text_prompt()` используется для обычных `.md` / `.txt` файлов, например description tool.

Jinja2 настроен через:

```python
Environment(
    loader=FileSystemLoader(PROMPTS_DIR),
    autoescape=False,
    undefined=StrictUndefined,
    trim_blocks=True,
    lstrip_blocks=True,
)
```

## 7. Реализована функция-обработчик tool

Файл:

```text
app/tools/handlers.py
```

Основной обработчик:

```python
search_knowledge_base(query: str, ips: str) -> dict[str, Any]
```

Зависимость от внешних данных реализована через чтение файла:

```text
app/data/knowledge_base.json
```

Это не заглушка `return "ok"`, а настоящий поиск по локальной базе знаний.

В `knowledge_base.json` сейчас есть записи:

```text
kb-001 — Ошибка авторизации в АИС Правоохрана
kb-002 — Ошибка загрузки данных в АИС ЦРСВЭД
kb-003 — Технический сбой приложения АИС Постконтроль
kb-004 — Общее обращение без определенного подразделения
```

Реализована простая scoring-логика:

```text
+10 если совпало подразделение;
+3 если подразделение пустое и запись общая;
+1 за каждое совпавшее слово;
+5 за точное совпадение симптома.
```

Поиск возвращает максимум 3 наиболее релевантных результата.

## 8. Реализован полный цикл tool_calls

Файл:

```text
app/client.py
```

Используется OpenAI SDK и Chat Completions API.

Зависимости:

```text
openai
python-dotenv
jinja2
```

Настройки читаются из `.env`:

```env
OPENAI_API_KEY=...
OPENAI_MODEL=gpt-4.1-mini
```

Основной цикл:

```text
1. Пользователь вводит запрос.
2. Загружается system prompt.
3. Формируется messages.
4. В модель отправляются messages + tools.
5. Если модель вернула tool_calls:
   - парсятся arguments;
   - вызывается Python-функция из TOOL_HANDLERS;
   - результат добавляется в историю как role: "tool";
   - выполняется второй запрос к модели;
   - возвращается финальный ответ.
6. Если tool_calls нет:
   - возвращается обычный текстовый ответ модели.
```

Реализованы функции:

```python
load_settings()
build_client()
build_initial_messages()
execute_tool_call()
append_tool_results()
run_chat()
main()
```

Важный момент: после первого ответа модели в историю добавляется assistant-сообщение с `tool_calls`, затем добавляется результат функции с ролью `tool`.

## 9. Проверены три сценария

Результаты зафиксированы в `README.md`.

### Сценарий 1. Запрос точно требует tool

Запрос:

```text
В АИС Правоохрана пользователь не входит в систему, пишет access denied. Есть типовое решение?
```

Результат:

```text
Модель вызвала tool: да.
Имя tool: search_knowledge_base.
Аргументы:
query = "Пользователь не может войти в систему, пишет access denied"
ips = "АИС Правоохрана"
```

Функция нашла запись:

```text
kb-001 — Ошибка авторизации в АИС Правоохрана
```

Финальный ответ модели: модель указала причину `access denied`, перечислила проверки учетной записи, ролей, блокировки и срока действия пароля, затем рекомендовала направить заявку ответственному администратору АИС Правоохрана.

---

### Сценарий 2. Запрос точно не требует tool

Запрос:

```text
Что такое база знаний в техподдержке?
```

Результат:

```text
Модель вызвала tool: нет.
tool_calls: [].
```

Модель дала обычное теоретическое объяснение без поиска по базе знаний.

---

### Сценарий 3. Пограничный случай

Запрос:

```text
Как обычно разбирают ошибку 500 в приложении?
```

Результат:

```text
Модель вызвала tool: нет.
tool_calls: [].
```

Модель обработала запрос как общий методический вопрос и дала общие шаги диагностики ошибки 500.

Вывод: запрос пограничный, потому что содержит технический симптом, но не указывает конкретную АИС и не содержит прямую просьбу искать типовое решение в базе знаний.

## 10. Реализовано логирование

Файл:

```text
app/logging_config.py
```

Логи пишутся в формате JSONL:

```text
logs/function_calling.jsonl
```

Одна строка — одно событие.

Реализованы функции:

```python
setup_logger()
write_log_event()
```

Для каждого запуска создаётся `run_id`, чтобы связать события одного запроса.

Для запроса с tool пишутся события:

```text
user_input
tool_selected
tool_result
final_answer
```

Для запроса без tool пишутся события:

```text
user_input
final_answer
```

В лог попадает:

```text
timestamp
event
run_id
user_text
model
tool_name
arguments
result
final_answer
usage_total_tokens
```

Формат подготовлен с прицелом на дальнейший переход к `structlog`.

## 11. Принятые соглашения по коду

На текущем этапе зафиксированы такие правила:

```text
1. Комментарии и docstring в коде — на русском языке.
2. Текстовый вывод через print — на русском языке.
3. Docstring оформляются по правилам Python:
   """Краткое описание действия функции."""
4. Для function calling используется OpenAI Chat Completions API.
5. Для промптов используется app/prompts/.
6. Tool description считается промптом и хранится отдельно от Python-кода.
7. В README не вставляются огромные JSON-ответы, только краткая фиксация результатов.
```
