# M6B5 — сравнение single- и multi-agent

## Сценарий и набор

Вход — вопрос пользователя технической поддержки о проблеме из базы знаний.
`researcher` находит подтверждённые факты через `search_knowledge_base` и возвращает только список источников; `writer` превращает этот список в связный ответ. Ожидаемый результат — краткое действие или честная эскалация, а при найденных документах ссылки вида `[1]`, `[2]`.

Обе реализации используют один и тот же инструмент из `experiments/common.py`: воспроизводимый локальный mock RAG по `app/data/knowledge_base.json`, который возвращает до трёх документов с score. Так исключены ключи API, Qdrant и различия корпуса. Набор из пяти вопросов: три прямых по БЗ (Правоохрана, ЦРСВЭД, Постконтроль), один многошаговый (кодировка файла и эскалация в ЦРСВЭД) и один вне БЗ (сброс пароля корпоративной почты).

## Реализации и воспроизведение

Multi-agent реализован ручным supervisor-графом LangGraph, а не через `langgraph-supervisor`: это позволяет явно фиксировать `Command(goto=..., update=...)`, `InMemorySaver` и счётчик handoff без новой зависимости. Supervisor последовательно передаёт shared state `researcher`, затем `writer`; это две передачи управления. Оба специалиста созданы через `langchain.agents.create_agent`. `stream_mode="updates"` печатается в консоль, а Mermaid получен непосредственно из `app.get_graph().draw_mermaid()`.

Single baseline — один `create_agent` с тем же tool и объединённой ролью. Чтобы замеры были детерминированными, LLM-вызовы выполняет локальная tool-capable модель эксперимента с usage metadata, а не внешний провайдер. Это сравнение накладных расходов оркестрации, а не benchmark качества конкретной коммерческой модели.

```powershell
uv run python -m experiments.multi_agent_langgraph
uv run python -m experiments.single_agent_baseline
uv run python -m experiments.evaluate_faithfulness
uv run python -m pytest tests/unit/test_multi_agent_experiment.py -q
```

Каждый скрипт запускает все пять вопросов; второй дописывает свои пять строк, не удаляя строки первого, в `experiments/results.json`.

## Результаты

Сырые результаты находятся в `experiments/results.json`; оценка судьи — в `experiments/quality_results.json`. LLM-as-a-judge faithfulness запускается только после получения этих ответов, передаёт судье ровно тот контекст, который вернул общий `search_knowledge_base`, и не переиндексирует RAG/corpus. Все ответы по БЗ содержат `[1]`, `[2]`; вопрос вне БЗ в обеих версиях корректно получает отказ без выдуманного решения.

| Метрика | Single-agent (среднее по 5) | Multi-agent (среднее по 5) | Δ |
| --- | ---: | ---: | ---: |
| Токены на запрос | 104 | 164 | +57.7% |
| LLM-вызовов на запрос | 2 | 3 | +50.0% |
| Latency p50 (мс) | 2.35 | 7.13 | +4.78 мс |
| Передач управления на запрос | 0 | 2 | +2 |
| Качество ответа (LLM-судья, faithfulness) | 1.000 | 1.000 | 0.000 |

Судья DeepSeek оценил все 10 записей (по 5 на реализацию); каждый ответ
признан полностью подтверждённым контекстом общего search tool. Это измеряет
только faithfulness, а не полноту поиска или пользовательскую полезность.

## Сопоставление с Anthropic

В данном контролируемом сценарии multi-agent потребляет **1.58×** токенов single-agent, но не улучшает качество. Это существенно меньше ориентира Anthropic: в их production Research multi-agent обычно расходует около 15× токенов чата и на внутреннем breadth-first research eval дал +90.2% к single-agent. Наш домен — короткая локальная БЗ с общим контекстом и одним последовательным retrieval, а не независимые параллельные ветви поиска; поэтому он не получает преимущества breadth-first исследования. См. [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system).

## Решение

**Не использовать multi-agent в дипломе.** Default agent-слой — один `create_agent` с tools: на пяти одинаковых вопросах он достигает того же качества при меньших токенах, меньшей p50 latency и без двух handoff. Это также соответствует предостережению Anthropic: области с общим контекстом и тесными последовательными зависимостями плохо подходят для multi-agent, тогда как его ценность проявляется при независимой параллелизации и большом объёме поиска. Supervisor-прототип остаётся в `experiments/`, поэтому не смешивается с production-кодом; к нему можно вернуться, если появится независимый breadth-first поиск по разным корпусам.
